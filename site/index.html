Onchain identity infrastructure for governments and institutions

Most components of an identity system have no reason to be recorded on a public ledger. Credentials, personal data and presentation flows belong on devices and between the parties concerned. A small set of functions, however, must be global, current and neutral: registries of control, validity, trust and uniqueness, of which every participant requires the same view, and whose availability must not depend on the party that recorded them.

This page sets out those components and the manner in which they compose. They are not adopted as a single programme. Each is useful independently, and each addition increases the value of those already deployed.

Note on scope This material is provided for general educational and informational purposes. It does not constitute legal, regulatory, financial or other professional advice and should not be relied upon as such. The implementation described is an unaudited proof of concept, intended to support evaluation rather than production deployment.

01

What belongs on a public ledger, and what does not?

Placement is determined by a single question: is this state useful only if every participant holds the same view of it, does it change over time, and must its availability survive the party that recorded it? Registries of control, validity, trust and uniqueness meet that test. Credential data does not, and is deliberately excluded.

Onchain

Coordination state

  • Who controls an identifier right now
  • Who vouches for whom, and for what
  • Whether a credential is still valid
  • Whether a person has already acted in a context
  • What a verifier publicly commits to asking for
  • Settlement between issuers and verifiers

None of this constitutes personal data. No entry is meaningful in relation to an identifiable individual on its own.

Never onchain

Personal data

  • Credential contents and attributes
  • Names, identifiers, document numbers
  • Biometrics or anything derived from them
  • Presentation logs — who showed what, to whom
  • Anything correlatable to a natural person

A public ledger is permanent. Personal data recorded on one cannot be withdrawn, corrected or erased, which constitutes both a compliance failure and an ethical one.

How should an institution sequence adoption?

The architecture is modular. Six stages are set out below, each producing an outcome that is useful independently: a decommissioned system, a discontinued vendor agreement, or a capability not previously available. Selecting a stage indicates what it delivers and which components it requires.

Note The stages are advisory. They set out an order that reduces delivery risk and establishes value early; only the dependencies recorded against each component are binding. An institution requiring uniqueness alone may deploy that component independently.

04

How do the components compose?

The following worked example illustrates composition. An application distributes an entitlement once per person rather than once per account, restricted to holders of a credential issued by an institution that the application's chosen authority has accredited, and without the application learning the identity of any claimant.

  1. Context binding. The proof is bound to this distribution, so the same person's activity in other contexts cannot be correlated with it.
  2. Recipient binding. The proof commits to the claimant's address, which renders a proof intercepted in transit unusable by any other party.
  3. Live policy verification. The issuer must hold a current accreditation from the chosen authority. Withdrawal of that accreditation halts claims in the following block, during the distribution.
  4. Proof and uniqueness. The pairing check executes in consensus, the credential's validity is confirmed against a recent tree root, and the uniqueness value is consumed, preventing any second claim.

The practical implication

Approximately forty lines of application code. No allowlist administration, no vendor integration, no verification service, and no personal data at any point in the system.

The application did not implement an identity system; it inherited one. Every registry deployed subsequently increases the capability of applications already in production, without modification to any of them.

This property is not reproduced by bilateral-integration architectures, and it is the substantive reason to build on shared public infrastructure rather than within a single institution's perimeter.

05

What does public infrastructure provide that a hosted system does not?

The following are procurement properties rather than ideological positions. Each addresses a question that arises routinely in institutional due diligence, and for which hosted architectures have no satisfactory answer.

Continuity

Infrastructure that outlives its operator

Evaluations routinely ask what becomes of issued credentials if a supplier is acquired or exits the market. The registries continue to resolve after any individual participant ceases to exist, because no participant hosts them.

Neutrality

No party controls access

Registration is permissionless and endorsement is recorded separately from it, so no operator is able to exclude a competitor, a jurisdiction, or an institution. Each relying party selects the authorities it treats as roots.

Simultaneity

Revocation ceases to be a distribution problem

Withdrawal of trust reaches every relying party at the same block. Trusted-list distribution, certificate revocation lists and status endpoints each carry a propagation interval during which stale information remains in circulation.

Exit

Low exit cost by construction

The implementation is open source and forkable, the data is public, and the interfaces are standard. Adoption creates no position that cannot be left without a redevelopment programme, which is the property distinguishing open infrastructure from a proprietary stack.

Verifiability

Trust-critical logic executes in consensus

The checks on which the system depends execute where any party may audit them and no party may amend them privately, rather than within a supplier's runtime, under contract, evidenced by an assurance report.

Shared cost

Infrastructure funded once

Institutions presently each operate a trust list, a revocation service, and a set of verifier integrations. This is the same function, implemented once, with the cost of operation distributed across the participants who benefit from it.

06

What are the limitations and open questions?

The following are stated directly, as a balanced evaluation requires them. None prevents a pilot deployment; each should inform its scope and design.

Anonymity sets

A privacy-preserving proof conceals the holder among the members of their credential tree, and no further. A tree containing several hundred members affords correspondingly limited protection, and the natural tendency to organise trees by cohort, jurisdiction or issuance date causes membership itself to become the disclosure. Maintaining sufficiently large anonymity sets is an operational discipline for which no party currently holds responsibility.

Revocation latency

Recent credential-tree roots remain acceptable for a configured interval, so that a proof already in flight is not invalidated by an unrelated issuance. That interval is also the revocation delay. Short intervals disrupt legitimate holders; long intervals leave revoked credentials briefly usable. The tension is inherent, and is tuned per tree rather than resolved.

Deployment domain

Cost considerations favour a layer 2 network, while neutrality and permanence favour layer 1, or layer 2 state checkpointed to it. Enforcing uniqueness consistently across networks remains an open research question rather than an engineering task.

Settlement

The settlement layer records payment per verification, but no mechanism compels a verifier to settle for a verification performed off the ledger. Coupling the two — a wallet releasing a presentation only against an observed settlement, for instance — is an open design question.

Proof cost

The hash function underlying the privacy path is expensive to execute on Ethereum at present. Issuance is economical on a layer 2 network and costly on layer 1. A protocol-level optimisation would materially change the economics of every design in this class simultaneously.

Scope

Proof of personhood is not included. The architecture consumes personhood credentials; it does not issue them. The determination of who constitutes a unique person remains with whichever issuers an institution chooses to accredit.

Each component is accompanied by a written specification covering its value case, interface, invariants, and the path from proof of concept to production, together with a reference implementation and tests. The implementation is deliberately minimal and has not been audited. It is intended to make the mechanisms legible for evaluation, not to be deployed as it stands.
